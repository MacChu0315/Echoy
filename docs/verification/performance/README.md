# Device responsiveness investigation (2026-10-10)

The user reported visibly choppy UI animation and very long waits after role or
density changes. The retained volume/limiter settings are outside this task.
Device updates use the user's ongoing authorization, verified identity and the
retained Recovery workflow. The frozen HTML and UI resource bundle are unchanged.

## Measured baseline

Instrumented package `6fb79108bf93` added the SDK's rendered-FPS log, UI tick/gap
and gallery-raster timing, and per-stage synthesis timing. It made no functional
change. Only events from its exact boot ID are used in [baseline.txt](baseline.txt).

- Silent Pulse home: 7.4–7.5 rendered fps despite no animation need, roughly
  140 ms between UI service callbacks (the callback work itself about 1 ms).
- Voice preparation: 48.95–49.00 s. Harmony phrase 2: 24.36 s. Pulse phrase 1:
  10.48 s. Dust phrase 1: 17.10 s. Most time is in actual sample synthesis.
- Harmony home while playing: about 1.3–1.4 rendered fps, up to 780 ms UI gaps.
- Synchronous gallery raster batches: 191–287 ms.

The target compilation explicitly uses `rv32imafcb...` / `ilp32f`; it does not
have hardware double precision in this configuration. The prior code evaluated
many double transcendental/filter operations for every sample. Separately, the
art raster repeated segment bounds/joins for small coverage blocks, evaluated
constant curves repeatedly, and repainted static home art periodically.

## Changes

The portable C synth now uses hardware single precision for sample processing,
job-owned sine lookup and cached triangle tables, integer oscillator phase,
exponential envelope recurrence with regular re-anchoring, and invariant filter
coefficient reuse. Event-to-frame rounding and RMS accumulation remain precise.
Very low/near-Nyquist Grain filters retain the old double-precision path to
preserve the full legal pitch range. The shared musical rules, compression and
normalization remain the same. No fast-math compiler flags or new dependencies.

Artwork retains the same raster coverage and RGB565 results: ring interiors and
invisible pixels skip expensive distance roots; constant curve values are
reproducibly generated by `tools/generate_art_tables.py`; path bounds/joins and
scanline intersections are calculated once for reuse. Color blending normally
uses float and falls back to the original double expression near truncation
boundaries. Static art no longer repaints continuously.

A workspace owned by each serialized UI instance holds geometry scratch and the
current dynamically rendered artwork. GSP's partial surfaces copy from that
raster instead of recalculating the same curves. Changes to plan contents,
role, dimensions, color, capture/active state, progress or energy invalidate it.
Controls and dynamic content remain real GSP objects; this is not a screenshot
of an application page. Allocation failure propagates during UI creation, and
workspace release follows the existing canvas-stop/flush barrier. No mutable
render or synthesis singleton is shared between independent UI instances.

  The user's existing live preview build is never rebuilt in place.

## First optimized hardware run

Package `ac24f401ee50` installed successfully; image identity, HEALTHY, commit,
partition and bootloader preservation checks passed. The user reported both UI
and preparation were markedly smoother. Its measured preparations were about
0.31 s Pulse, 0.79–0.82 s Voice, 0.42 s Dust and 0.60–0.62 s Harmony. These are
real user-operation samples from different recordings, not a controlled
same-seed before/after benchmark.

Complex active artwork still reached only about 4–5 fps, and render task stack
headroom fell to 1,284 bytes on Harmony. Those observations prompted the final
workspace/cache and exact blend changes above; the first candidate is not the
final result. Installation and measurements for the final package follow below.
