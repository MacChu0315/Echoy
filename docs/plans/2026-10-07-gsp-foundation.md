# Echoy GSP foundation implementation plan

Goal: preserve the supplied prototype and establish a working GSP application
with shared C UI, reproducible reference captures, and native interaction evidence.
The user's approved HTML -> GSP/C -> simulator -> hardware workflow is the spec.
Continue locally in `feat/echoy-rebuild`; no device writes or remote publication.

## Decisions

- `reference/` is immutable input; supplied verification is historical evidence.
- `projects/echoy` is generated by the official CLI and owns firmware and PC code.
- Use utils and BSP at the revisions in `../dependencies.json`; SDK lives in an
  isolated sibling `.toolchains` checkout. Existing SDKs remain untouched.
- Native controls and text stay native. Central role drawing may use GSP Canvas,
  subject to verifying the pinned bridge's support. No screenshot-based page.
- Use monotonic microseconds for a portable recording state model; hardware and
  PC provide time and output services. No microphone recording or automatic resume.
- Preserve exact 480x480 screen coordinates, including existing narrow controls.
- Treat fonts, rounding and RGB565 as measured rendering differences, not permission
  to move controls or alter copy. Unavoidable visible changes require user review.

## Review focus

- Late work after cancel must not restart output.
- Down/up/held input must not produce duplicate taps.
- Empty or boundary recordings must not erase the existing seed.
- Asset or template changes must not silently alter the baseline HTML.
- Simulator success is not sound synthesis, distributed-clock or hardware acceptance.

## Subsequent application work

After the native home foundation is proven: role/settings/detail/fault pages,
all twelve phrase algorithms and audio, multi-device model/transport, then physical
integration and acceptance. Preserve the prototype's in-memory semantics unless
persistence is explicitly requested. Browser-only export/remove actions need an
explicit device mapping before claiming full product parity.

## Verified outcome

This plan's home foundation is implemented and checked. Evidence is in
`../verification/README.md`; all later application work above remains unfinished.
The recording model has 7 behavior groups, native GSP checks cover 9 groups,
and the same UI sources build for ESP32-S31 with zero warnings. No board was written.

Review corrections: initialize mutable state before registering render-task
callbacks; preserve recording/preview feedback; verify shutdown status and
held-input de-duplication; rasterize only the dashed border decoration.
The 16-dot feedback uses a small GSP Canvas so changing dot widths reproduces
the reference's dynamic spacing without an independent UI implementation.
