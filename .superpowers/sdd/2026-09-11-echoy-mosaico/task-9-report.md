# Task 9 report — desktop firmware simulator

Status: DONE. Base: `8202111`. Work remains on `feat/echoy-mosaico`.

## Delivered

- `tools/echoy-sim/run.py` implements all three requested entry points: pinned
  reference HTML, three-instance firmware simulation and `--headless --scenario
  all`. The Python bridge uses the standard library only.
- `pc/platform_pc.c` is a development-only executable linked to the existing C
  core/control/protocol, LVGL view/touch and audio DSP. Each virtual device owns
  a separate process. The bridge supplies a bounded fake clock and carries the
  actual wire packets; it does not implement sessions in Python or JavaScript.
- The reference page is served byte-for-byte with SHA-256
  `d23c51b025b44a0d2d11a3ad5a371abd4a2117adb8e742491e838af6dc4c0bb5`.
  Both modes bind only 127.0.0.1. An explicit asset dictionary permits no path
  resolution, directory listing, repository files or Sync directory access.
  API requests validate Host/Origin, content type, byte bounds and strict JSON.
- Firmware HTML reuses the pinned shell/localization/spatial/desk/guide modules,
  without loading the original JS engine, session, renderer or synthesizer.
  Shell x/y stop at DuijuSpatial; the C product receives contact IDs only.
  Screen touch coordinates go to the real `echoy_view_pointer` entry.
- Every `.screen` displays a real 480×480 LVGL PNG frame. `pc/ui_frame.h` shares
  the display/flush adapter with the existing fixture renderer. Snapshot,
  framebuffer and C PCM publication carry the same revision and a bridge
  sequence; stale display/audio delivery is rejected.
- AudioWorklet consumes bounded 48 kHz stereo PCM generated by the C DSP, with
  browser master gain outside the product. The headless suite emits an offline
  WAV and verifies nonzero output and exact duration.
- The shell retains snap previews, collision rollback, pointer cancellation,
  keyboard movement, panning/scrolling, reserve/power, third device, six guide
  steps, reopen/locate, quick reference, Chinese/English, diagnostics, faults,
  logs and HTML-to-firmware mapping. The guide reads C observations only.
- The adapter models readiness with fixed C events. Reboot issues a new matching
  core/protocol boot ID. Sync-fault injection both drops negotiation packets
  and publishes the actual C `sync-failed` state; restoration allows the real
  protocol to negotiate again. No production firmware source or sibling repo
  was changed. The runner is not linked into ESP-IDF.
- `README.md` documents entry points, limits, ownership and hardware boundaries.
  Generated evidence and temporary browser profiles live under ignored
  `output/sim/` only.

## RED and fixes discovered by verification

`output/sim/red.log` records the initial failing entry-point/bridge contract
suite before implementation. The tests were written before `run.py` existed.
The first complete run exposed mismatched core/protocol boot generations on
power-on, preventing C from joining; this was fixed through explicit BOOT and
protocol initialization rather than weakening wire validation. A subsequent
check required the sync-failure screen to report C's failure state, not merely
an adapter flag.

Browser navigation initially stalled before any page script ran. CDP frame-tree
and network evidence isolated the wait to Chrome's cookie/keyring initialization.
The test now uses an isolated profile and `--password-store=basic` /
`--use-mock-keychain`. Playwright CLI was unavailable and its npm lookup failed
with EAI_AGAIN, so the repository's existing local Chrome/CDP approach was used.
Early touch and stow harness failures were corrected by observing the C role
commit before touching the perform page and sampling pointer coordinates after
scrolling. Product timing was not loosened to satisfy these checks.

## Limits / concerns

This is explicitly development simulation. Desktop contact and fake time do not
establish physical identity, real wireless delay, acoustic synchronization or
hardware endurance. These remain Task 10 / hardware acceptance work. No actual
speaker listening, physical devices, flash, remote writes or sibling changes
were performed. Closing the page stops new PC injections/output; it does not
send pause/shutdown to firmware, and actual MCU execution is independent.

The report is explicitly added alongside the existing tracked Task 6–8
`.superpowers` reports. Reproducible tool instructions are committed in `tools/echoy-sim/README.md`; generated logs/screenshots/PCM are not committed.
