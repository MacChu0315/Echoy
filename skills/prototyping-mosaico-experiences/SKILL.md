# 验证 Mosaico 的核心体验

## 适用范围

把想法变成可判断的体验，而不是先补齐所有页面和外设。本技能是试用版；尚未完成独立 agent 的有／无 skill 对照。

先使用已有目标、有效决定和当前材料。明确的小改动不重新走产品定义。用户只讨论方向时先给方案；用户已要求制作时，在现有授权内推进。关键输入确实缺失时，一轮只问一个影响结果的问题。

## 工作方式

1. **确定一段核心体验。** 用“谁在什么场景，做什么，会感知到什么变化，为什么还愿意继续”描述最小片段。分清已确认要求与假设。先证明这个变化，不以页面数量代替价值；是否需要单机成立由当前产品决定。
2. **读取当前设备依据。** 核对硬件／BSP 版本、显示与触控契约、按键、扩展槽和资源并发限制。分清硬件事实、项目选择、未知能力和模拟条件，不从 Echoy、示意外壳或通用芯片知识补成确定能力。
3. **检查动作是否同时成立。** 需要持续拼接时，检查倾斜、握持、滑动是否破坏连接或造成误触。没有测距依据时，不把距离当可用输入；没有资源依据时，不假设外设可以同时使用。
4. **隔离模拟器与产品。** 网页搬动、故障注入、预览音量留在设备外；设备内提供核心情景需要的控制与反馈。宿主坐标转换为接触等产品事件，业务规则不依赖整个桌面的坐标或全知状态。一个浏览器时钟只是模拟条件。
5. **实现可体验片段。** 操作确实驱动内容变化；画面、声音和状态读取对应的业务状态，待生效内容单独反馈。随后补当前片段必需的加载、取消、失败、返回和恢复。需要时设计多机或异步规则，不给简单单机强加会话协议。
6. **只扩大值得继续验证的部分。** 用户感知不到核心差异时，先修改因果关系或呈现方式，不靠更多设置、动效和解释掩盖。保留认可内容。沿用原工程构建方式；需要离线单文件交付时可以打包，内部仍保持职责分离。

## 交付与验收

给实际存在的体验入口、核心操作与预期变化、模拟边界和未验证项。向固件交接时，在已有记录或小表中对应“产品行为 → 已有基础与应用新增工作 → 真机验收”，不要求新建完整文档体系。

分别检查体验变化是否发生、实现是否符合规则、真机是否证明可行。浏览器运行不证明磁吸识别、无线对时、功耗、真屏可读性或实体扬声器表现；相关示例存在也不证明应用功能完成。未执行项写明未执行。
